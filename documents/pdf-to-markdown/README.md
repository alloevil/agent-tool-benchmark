# PDF → Markdown: pymupdf4llm vs markitdown vs docling vs pdftotext (vs marker)

Same-machine, same-fixture benchmark of PDF→Markdown conversion tools used in
agent document-ingestion pipelines, run on 2026-08-19.

**TL;DR** — On these synthetic born-digital PDFs, **pymupdf4llm** wins on
every axis that matters: full heading/table/code recall, the only correct
two-column reading order among the fast tools, intact CJK, and ~0.65 s per
call at ~120 MB of dependencies. **docling** matches its structure scores but
takes **~10 s per document on CPU** and 5.5 GB of installed dependencies — and
its CJK output is subtly corrupted (CJK Radicals substituted for ideographs:
`水` U+6C34 → `⽔` U+2F54, invisible to the eye, fatal to search/embedding).
**markitdown** and the **pdftotext** baseline produce *plain text with pipe
tables*, not markdown structure (zero headings marked), and both interleave
two-column text. **marker** could not be run (model CDN unreachable from this
network — see Limitations).

## What this measures

Agents that ingest PDFs need markdown that (a) preserves document *structure*
(headings, tables, code) so downstream chunkers and models can use it, and
(b) preserves *content* (reading order, CJK fidelity). This benchmark feeds
five deterministic reportlab-generated PDFs — whose source text is hardcoded
ground truth — through each converter and scores the output with purely
mechanical string checks (no LLM anywhere, no fuzzy similarity):

| Metric | Definition (see `run.py` docstring for exact rules) |
| --- | --- |
| heading recall | expected heading text appears on a `#`-prefixed line. Emitting the text *without* `#` scores 0 — the benchmark is about markdown structure, not text survival |
| sentence / cell / code recall | expected string appears as a whitespace-collapsed substring (markdown decoration stripped first) |
| reading order | for ordered pairs (A, B): first occurrence of A precedes B. Column-wise reading passes all 22 pairs; interleaving across columns fails cross-column pairs |
| CJK intact | each Chinese sentence appears verbatim, character-for-character, after removing all whitespace |

Every conversion runs in a fresh subprocess, twice: run 1 = cold (includes
import + model load + any first-time model download), run 2 = warm. Tables
below report **warm** times; cold times are in `results.json`.

## Task design

Five single-page PDFs, generated by `fixtures/generate_pdfs.py`; the same
literals that lay out the PDF are written to `fixtures/expected/*.json`:

| # | Fixture | What it probes |
| --- | --- | --- |
| 01 | simple | H1/H2/H3 hierarchy, paragraphs, inline bold |
| 02 | table | 4×6 gridded data table with styled header row |
| 03 | two-column | true two-frame layout; 4+4 sentences give 22 ordered pairs (3+3 consecutive within-column + all 16 cross-column pairs) — cross pairs detect row-major extraction, within-column pairs detect line scrambling |
| 04 | code-and-list | 11-line monospace code block + 2-level nested bullet list |
| 05 | cjk | Chinese headings/paragraphs (CID font STSong-Light) + mixed CJK/Latin sentence |

## Results

Warm run, fresh subprocess per conversion. `results.json` has cold times,
byte counts, and per-metric detail; raw converter outputs are in `outputs/`.

### Structure & fidelity

| Fixture · metric | pdftotext | pymupdf4llm | markitdown | docling | marker |
| --- | --- | --- | --- | --- | --- |
| 01 heading recall (4 headings) | 0.00 | **1.00** | 0.00 | **1.00** | not run |
| 02 table cell recall (24 cells) | 1.00¹ | **1.00** | **1.00** | **1.00** | not run |
| 03 reading order (22 pairs) | 16/22 ✗ | **22/22 ✓** | 12/22 ✗ | **22/22 ✓** | not run |
| 04 code line recall (11 lines) | 1.00¹ | **1.00** | **1.00** | 1.00² | not run |
| 05 CJK sentences intact (3) | 1.00¹ | **1.00** | **1.00** | **0.00** | not run |
| heading recall, all 5 fixtures | 0/10 | **9/10** | 0/10 | 8/10 | not run |

¹ pdftotext emits plain text: content survives but nothing is marked up

### Speed & cost

| Measure (mean over 5 fixtures) | pdftotext | pymupdf4llm | markitdown | docling | marker |
| --- | --- | --- | --- | --- | --- |
| warm wall time / doc | **0.05 s** | 1.07 s | 1.03 s | 12.3 s³ | not run |
| cold wall time / doc | 0.06 s | 1.05 s | 1.05 s | 11.7–13.2 s³ | not run |
| output tokens (5 docs, cl100k) | 1093 | 1117 | 1311 | 1199 | not run |
| installed footprint | (system) | ~120 MB | ~10 MB | **5.5 GB + 642 MB models** | 5.3 GB + ~1 GB models |

³ docling per-doc times ranged 11.7–13.2 s across this run (each conversion

disk). Absolute times vary with machine load run-to-run — an earlier run of
the identical matrix measured 7.6–8.5 s/doc — but the ~10× gap to
pymupdf4llm and the ~200× gap to pdftotext are stable. Read every docling
cell as "~10 s per document on this CPU".

## Key findings

1. **"Markdown output" is not binary — two of the four tools produce almost
   none.** markitdown and pdftotext scored 0/10 on heading recall: every
   heading survives as *text* but nothing carries `#`. For a RAG chunker that
   splits on headings, their output is structurally equivalent to `pdftotext`
   — which is 20× faster than markitdown and free.
2. **Two-column reading order cleanly splits the field.** pymupdf4llm and
   docling read column-by-column (22/22 pairs). **pdftotext interleaves the
   columns paragraph-wise** — its output is A1 B1 A2 B2 …, which keeps
   within-column order (and accidentally passes 10 of the 16 cross-column
   pairs, hence the flattering-looking 16/22) but breaks the actual reading
   flow after every paragraph. markitdown (pdfminer.six) is worse still: on
   top of interleaving it **scrambles words within lines** — the output
   contains `operators  hydropower  Downstream` and `ice  concentrates
   above  The  remaining` — destroying two of the eight key sentences
   outright (sentence recall 0.75, 12/22 pairs; see
   `outputs/markitdown/03-two-column.md`).
3. **docling's CJK is silently corrupted.** It scored 0/3 on
   character-exact CJK: its extraction maps common ideographs to visually
   identical **CJK Radicals** (`水` U+6C34 → `⽔` U+2F54, `工` → `⼯`, …) in
   both headings and body. The text *looks* perfect and even reads fine, but
   string search, embeddings, and any exact-match retrieval on it silently
   fail. pymupdf4llm, markitdown, and pdftotext all reproduced every Chinese
   sentence byte-exactly, including the mixed CJK/Latin one.
4. **docling buys nothing here for its 12× latency and 45× install size.**
   Its layout model earns identical structure scores to pymupdf4llm's
   heuristics on born-digital PDFs (its one win: pipe tables with proper
   column padding; its losses: CJK corruption — which also zeroes both CJK
   headings, since the `##`-marked text no longer matches — and the
   flattened code block). Layout models should pay off on scanned/complex
   documents — which this benchmark deliberately excludes (no OCR scenario).
5. **Nested list markers degrade everywhere.** pymupdf4llm turned level-2
   bullets (◦) into stray `I` glyphs; docling flattened both levels to one
   and rendered ◦ as `n`. Content survived (scored via sentence recall);
   list *nesting* did not survive any tool.
6. **Everything is deterministic.** All 20 (tool, fixture) conversions
   produced byte-identical output on cold and warm runs (`deterministic`
   flag in `results.json`), so single-run scores are stable for these tools
   on these fixtures.

## Verdict

- **Default choice: pymupdf4llm.** Best structure scores, correct column
  order, byte-exact CJK, 0.65 s/doc, pip-installable in seconds. (Note
  PyMuPDF is AGPL-licensed — check your distribution constraints.)
- **docling:** only worth ~10 s/doc + 6 GB if you need its layout model for
  scanned or visually complex documents — and **do not use it on CJK
  documents** without checking for the radical-substitution corruption.
- **markitdown (for PDFs):** structurally a plain-text extractor with pipe
  tables; wrong column order. Its value is the many *other* formats it
  handles, not PDF quality.
- **pdftotext:** unbeatable when you only need text: 20× faster than
  anything else and near-correct column handling. No structure at all.

## Reproduce

```bash
# light tools into the repo venv
.venv/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple \
    reportlab pymupdf4llm "markitdown[pdf]" "pillow==11.2.1"

# docling needs its own venv (torch, ~5.5 GB)
python3 -m venv /path/to/venv-docling
/path/to/venv-docling/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple docling

cd documents/pdf-to-markdown
../../.venv/bin/python fixtures/generate_pdfs.py   # regenerate fixtures (byte-identical)
DOCLING_PYTHON=/path/to/venv-docling/bin/python \
  ../../.venv/bin/python run.py \
  --not-run 'marker=model weights unreachable from this network'
```

Without `DOCLING_PYTHON`/`MARKER_PYTHON`, run.py auto-detects missing imports
and records those columns as `not_run` with the probe error.

## Limitations

- **Synthetic fixtures from a single generator.** All five PDFs come from
  reportlab, so every tool faces reportlab's particular text encoding, font
  handling, and content ordering. Real-world PDFs (LaTeX, Word, InDesign,
  scanners) exercise different code paths; treat scores as an upper bound.
- **No scanned/OCR scenario.** No tesseract on this machine and all fixtures
  are born-digital with a clean text layer. This is precisely the regime
  where docling/marker's ML pipelines are supposed to shine, so the "docling
  buys nothing" finding must not be extrapolated to scanned documents.
- **marker-pdf: not run.** The package installed, but its model weights
  (~1 GB) could not be fetched from this network: `models.datalab.to`
  (surya's S3 CDN) stalls indefinitely, and the HuggingFace fallbacks
  (`huggingface.co` and `hf-mirror.com`, repos `datalab-to/*`) delivered
  ~2–15 kB/s. Three attempts totalling ~55 minutes were aborted; the column
  is recorded as `not_run` in `results.json` with this reason.
- **Single run per cell** (though a cold/warm pair each, and all outputs were
  byte-identical across the two runs, so variance in *scores* is nil; timing
  variance is unmeasured).
- Scoring is substring-based: it measures *survival and ordering* of known
  strings, not layout beauty, table column alignment, or indentation
  fidelity (docling's flattened code block still scores 1.0 on code recall).
- One page per fixture; multi-page behavior (headers/footers, cross-page
  tables) untested.
